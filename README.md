
| Table | Key columns | Notes |
|---|---|---|
| `users` | id, name, email | Single default seeded user (no real auth, per assignment scope) |
| `meetings` | id, title, date, duration_seconds, media_url, owner_id | Core meeting record |
| `participants` | id, name, email | Deduplicated across meetings |
| `meeting_participants` | meeting_id, participant_id | Many-to-many join table — enables real SQL filtering by participant instead of string-matching a JSON blob |
| `transcript_segments` | id, meeting_id, speaker_name, start_time_seconds, end_time_seconds, text, order_index | `speaker_name` is a denormalized string, not a FK to `participants` — see Assumptions below |
| `summaries` | id, meeting_id (unique), overview, generated_at | One-to-one with meeting |
| `topics` | id, meeting_id, title, start_time_seconds, order_index | Powers clickable "chapters" that seek the player |
| `action_items` | id, meeting_id, text, assignee, is_completed, source_segment_id, created_at | `source_segment_id` links an action item back to the transcript line it was extracted from |

**Design rationale:** the participant join table (rather than a JSON array on `meetings`) allows filtering meetings by participant with a real SQL join — a relational approach rather than string-matching inside JSON.

## API Overview

Full interactive docs (auto-generated by FastAPI) are live at `/docs` on the backend URL. Summary of key endpoints:

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/meetings` | List meetings — supports `q` (title search), `participant` (filter), `sort` (recent/oldest/title) |
| GET | `/meetings/{id}` | Full meeting detail — transcript, summary, topics, action items |
| POST | `/meetings` | Create a meeting (paste/upload transcript → auto-generates summary, topics, action items) |
| PUT | `/meetings/{id}` | Update meeting metadata (title, participants) |
| DELETE | `/meetings/{id}` | Delete a meeting and its associated data |
| GET | `/meetings/{id}/transcript/search` | Search within a single meeting's transcript |
| GET | `/search` | Global search across all meetings |
| POST | `/meetings/{id}/action-items` | Create an action item |
| PUT | `/action-items/{id}` | Update / mark an action item complete |
| DELETE | `/action-items/{id}` | Delete an action item |

## Features Implemented

- **Meetings Library**: cards with title/date/duration/participants; search by title, filter by participant, sort by recency/oldest/title
- **Meeting Detail**: interactive transcript with speaker labels + timestamps, simulated media player with seek bar, bidirectional sync (click transcript → seek player, and vice versa), clickable topic chapters
- **AI Summary & Notes**: mocked summary generation, extracted action items, topic outline — all generated from the transcript text at creation time
- **Full CRUD**: create meetings (paste transcript), edit title, delete meetings; create/edit/complete/delete action items
- **Fireflies-style UX**: navbar with Meetings/Integrations/Team/Settings placeholders, modals, toasts, card-based purple-accented layout
- **Persistence**: all data in SQLite via SQLAlchemy (see Known Limitations for Render-specific caveat)

## Assumptions & Documented Simplifications

- **No real authentication** — a single default user ("Alex Carter") is seeded and used throughout, per assignment scope.
- **`speaker_name` is a string, not a FK to `participants`** — real transcript exports (VTT/JSON from Zoom, etc.) typically contain speaker labels as plain strings. Mapping them reliably to structured participant records is non-trivial and out of scope; documented here as a deliberate simplification.
- **No real audio/video file** — the media player uses a simulated clock rather than an actual `<audio>`/`<video>` element with a real file, since real transcription/recording was explicitly out of scope for this assignment.
- **AI summary/topics/action items are mocked heuristics**, not real LLM calls — generated deterministically from transcript text via simple parsing rules in `utils.py`, per the assignment's note that "summaries can be mocked, seeded, or generated from uploaded transcript files."
- **Integrations, Team, and real-time bot** sections are placeholder "Coming Soon" UI, as permitted by the assignment.

## Known Limitations

- **Render free-tier cold starts**: the backend spins down after ~15 minutes of inactivity. The first request after idle time can take 30–60 seconds to respond while the instance wakes up. The frontend handles this with a loading state, a request timeout, and a retry option rather than hanging indefinitely.
- **Render free-tier ephemeral disk**: the SQLite database resets on every service restart/redeploy, at which point it's automatically re-seeded with the 4 sample meetings on startup. This means CRUD changes (new meetings, completed action items, etc.) do not persist long-term on the free tier. A production deployment would use Render's persistent disk or a hosted Postgres instance instead.

## Running Locally

### Prerequisites
- Python 3.11+
- Node.js 18+

### Backend

```bash
cd backend
python -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # macOS/Linux
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

The backend will auto-seed 4 sample meetings on first startup. Visit `http://127.0.0.1:8000/docs` to confirm it's running.

### Frontend

```bash
cd frontend
npm install
copy .env.local.example .env.local    # Windows
# cp .env.local.example .env.local    # macOS/Linux
npm run dev
```

Set `NEXT_PUBLIC_API_URL` in `.env.local` to `http://localhost:8000` for local development. Visit `http://localhost:3000`.
